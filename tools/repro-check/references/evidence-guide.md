# Evidence guide: where proof lives in a reproduction package

The rubric names evidence; this file says where to find it and what good looks
like when you do. A check whose evidence cannot be located here is a check
nobody else can execute.

## Environment

**Where it lives.** In an eval bundle: the opening lines of the repro report,
often before any command, and sometimes scattered through the prose instead of
collected under a heading -- read the whole report before concluding a fact is
absent. The issue context and the repo-facts block say what the environment has
to be measured against: the issue's own "Operating system:" line, the version it
targets, the release the repo shipped. Live: the student's draft, and the
issue's template fields on GitHub.

**What good looks like.** The facts a stranger needs to land on the same
behavior, pinned: the OS and its version, the language or tool version, the
versions of the dependencies the failure runs through, and the repo commit SHA
or release tag. The test is not length but decisiveness. Read the issue first
and note which facts it treats as load-bearing -- if it says debug builds panic
where release builds wrap silently, the build profile is load-bearing and its
absence is a hole no amount of other detail fills. If the report ran a different
version or platform than the issue targets, that is not automatically wrong, but
the difference has to be named rather than left for the reader to notice.

## Steps

**Where it lives.** The body of the repro report: the commands it ran, the
fixture or file it created, the UI actions it took, in the order it took them.
Sometimes embedded in a shell transcript rather than written as a list; a
transcript that shows the commands counts.

**What good looks like.** A stranger with a clean checkout can get from nothing
to the shown behavior without guessing. Every command is given in full rather than described. Every fixture is constructible: shown, generated by a command in the report, described precisely enough to rebuild ("a minimal `env.yml` with a valid `dependencies:` list plus a `category:` section"), or named as the issue's own input used verbatim. The starting state is constructible: "on a fresh clone at commit
X" is constructible, "in my working repo" is not. Terseness is not a defect --
four lines that name the setup and the trigger beat a page that never says which
command was run. The failure mode to watch for is the instruction that only
makes sense to its author: "run the command", "use the same file as before",
"set it up as usual".

## Behavior shown

**Where it lives.** The artifacts: pasted output blocks, stack traces, log
excerpts, screenshots, exit codes. Read each one against the failure the issue
describes -- its error text, its stated wrong outcome -- which lives in the
issue context section of the bundle.

**What good looks like.** The artifact shows the failure the issue names, and a
reader can see the match without being told. Matching means same error type or
message, or same observable wrong outcome; it does not mean byte-identical. File
paths, line numbers, timestamps, host names, and version strings differ on every
machine, and a panic at a different line of the same file is still that panic.
What is *not* a match: a different error entirely, a setup or dependency failure
that never reached the code in question, a crash the issue never mentions, or
the right error produced by an input the issue did not specify. That last one is
the hardest to see and the most common way a confident report is wrong -- the
artifact looks convincing, and it is proof of something else. When you cannot
tell whether an artifact matches, the report has not shown it.

## Honesty

**Where it lives.** At the seam between what the report says and what it pastes.
Claims live in the prose: result statements, causes, counts, scope ("on all my
machines", "every time"), comparisons, second configurations. Backing lives in
the artifacts beside them.

**What good looks like.** Every checkable claim has an artifact under it, and
the conclusion the report states is the one its artifacts support. An evidenced
"could not reproduce" is a full pass and one of the most useful things a report
can say: the artifact showing the failure's *absence*, with the environment and
steps that produced that absence, is proof. What fails is asserting past the evidence: a cause the report never tested, a scope it never measured, a reproduction it never shows. A cannot-reproduce meets this standard easily: its artifact is the attempt under the issue's own conditions, and naming what differed from those conditions is the report doing its job rather than hedging. Note the asymmetry -- a report making no checkable
claim at all has not thereby satisfied anything; it has simply failed to produce
proof, and reads as a me-too comment however strongly it is worded.

## Comms

**Where it lives.** The claim comment, read against the issue it claims. Both
comments read against the repo-facts block's contribution-policy line and its
bug-report-template line. Live: `CONTRIBUTING.md` and the docs it links,
`AI_POLICY.md` or similar, and the PR and issue templates, any of which may
carry a disclosure requirement.

**What good looks like.** The claim names this issue's own specifics -- the
function, the file, the command, the behavior -- so it could not be pasted under
any other issue, and it promises an investigation rather than an outcome. A
claim that promises a fix or a date has written a cheque the author cannot cash
before reproducing anything. On the repo's terms: if the contribution policy
requires disclosing AI assistance, both comments disclose it, and this holds
however good the proof is, because a contribution the repo cannot accept on its
own terms is not ready to post. Silence is not a requirement -- most repos state
nothing, and that constrains nobody. Where the repo publishes a bug-report
template, the facts it asks for that this issue's behavior depends on should be
present; the template is a statement of what this project's maintainers need in
order to act.
