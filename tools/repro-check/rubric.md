# Rubric: is this reproduction package ready to post?

A package is ready when a stranger could re-run it, the evidence shows the
issue's behavior rather than an adjacent one, and the words say exactly what
happened. Every check below reads the artifacts, never the formatting: a terse
complete report is ready, and a long confident one with nothing pasted is not.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| behavior-matches | The output, log, or artifact the repro report pastes, read against the failure the issue describes (its error text, its stated wrong outcome) | The pasted artifact shows the specific failure the issue names: the same error type or message, or the same observable wrong outcome. Incidental differences do not fail it -- file paths, line numbers, timestamps, version strings, and host names differ on every machine, and a matching failure with a different path is still a match. Fail when the artifact shows a *different* failure: another error, a setup or configuration error, a dependency failure, or a crash the issue never mentions. **When the report's stated result is a cannot-reproduce**, this check asks a different question: did the attempt target the issue's behavior? Pass when the artifact shows the issue's own scenario being exercised -- its input, its command, its conditions -- and shows what happened instead of the reported failure. The absence of the failure is the finding, and an artifact showing that absence under the issue's conditions is a pass, not a miss. A report that names a condition it could not create -- a limit it could not force, a platform it lacked, a scenario it did not test -- is doing this check's work, not failing it; that admission is what makes the negative result usable to a maintainer. Grade `unclear` when the report pastes no artifact at all. | required |
| input-matches | The input the repro report says it exercised (command, document, payload, or UI action), read against the input the issue specifies | The report exercised the input the issue specifies. The load-bearing elements are the same: the operator, the flag, the values, the order, the field that triggers the bug. Incidental differences are fine -- a renamed file, a different directory, reformatted whitespace. Fail when a load-bearing element differs, even slightly, because a near-miss input reproduces a different bug and calls it this one. If the issue specifies no particular input (a UI-state bug, a startup crash), this check passes and `behavior-matches` carries the target. | required |
| claims-backed | Every factual statement the report makes about what happened, read against the artifacts pasted alongside it | The report pastes at least one artifact from a run it actually made, AND every further run, count, comparison, or second configuration it claims has its own artifact. What must be backed is the report's conclusion. A secondary or corroborating run may be reported inline without its own block -- "dropping `-r '$1'` from the same command reports 1, 4, 7, 10 correctly" is supporting detail next to an artifact that already establishes the finding. A repeated or varied run needs its own artifact only when it carries weight the shown artifact does not: "I ran it ten times with identical results" is backed when the pasted artifact already shows that result and the conclusion drawn is no stronger than it, and unbacked when the repetition is being used to shore up a conclusion the artifact alone does not support. A report that asserts behavior and shows nothing fails, whatever its tone or length: having made no checkable claim is not the same as having backed one. | required |
| outcome-honest | The report's stated conclusion, read against what its own artifacts actually show | What the report says happened is what its artifacts show. An evidenced "could not reproduce" passes in full -- reporting that faithfully is a real result, and the artifact showing the *absence* of the failure is the proof. Fail when the report asserts more than it shows: a cause it did not test, a scope it did not measure ("happens on every machine"), or a reproduction its artifacts do not demonstrate. | required |
| env-recorded | The environment facts the report states (OS, language or tool version, dependency versions, repo commit or release, build profile), read against what the issue's own description makes load-bearing | The report names the environment facts a stranger would need to land on the same behavior, specifically the ones the issue itself treats as decisive. When the issue distinguishes builds or platforms -- debug panics where release wraps, Windows only, one version and not the next -- the report says which side it was on. Fail when a fact the issue's behavior depends on is absent. Completeness for its own sake is not the standard: a terse environment line that pins what matters passes, and a long one that omits the deciding fact does not. | required |
| steps-followable | The report's account of what it did, read as a stranger with a clean checkout would read it | A stranger could get from a clean checkout to the shown behavior using only what the report states, without guessing a value, a command, or a starting state. Terseness is not failure: four lines that name the setup and the trigger pass. The standard is constructible, not transcribed: a fixture described precisely enough to rebuild ("a minimal `env.yml` with a valid `dependencies:` list plus a `category:` section"), or identified as the issue's own input used verbatim, is given. Fail when the reader would have to guess -- "run the command" without saying which, a fixture whose contents are neither shown nor derivable from the issue, a starting state the reader cannot construct. | required |
| conventions-respected | The repo-facts block's contribution-policy and bug-report-template lines, read against what the claim comment and repro report actually contain | The comments satisfy the requirements the repo states **of comments**. Read the policy for its scope before its content: a disclosure duty written for pull requests ("state the tool and extent in the pull request") says nothing about an issue comment, and a policy asking only that comments be written by a human in their own words is satisfied by a human-voiced comment that never mentions tooling. Where the policy does reach these artifacts -- "all AI usage in any form must be disclosed", "AI-assisted issues and comments" -- it demands an affirmative statement, and comments containing no such statement do not satisfy it. The question is not whether you can tell an assistant was used; it is whether the package contains the disclosure the repo asks for. If the repo's bug-report template names required facts, the report supplies the ones this issue's behavior depends on. Silence passes: a repo that states no policy imposes no requirement. Fail when a stated requirement goes unmet, however good the proof is -- a report that cannot be accepted on the repo's own terms is not ready to post. | required |
| claim-grounded | The candidate claim comment, read against the issue it is claiming | The claim names this issue's own specifics -- the function, file, command, or behavior at stake -- and says what its author will do next. Fail on a claim that could be pasted under any issue in any repo ("+1", "me too", "claiming this one"). Fail on one that commits to a deliverable its evidence cannot support: a fix by a date, or a fix proposal promised on the strength of a diagnosis this package never demonstrates. Naming a direction of investigation is not a promise -- "find where the prompt decides to appear and make that case either warn or pass `--include-untracked`" is a plan, and a plan offered next to a reproduction that backs it is what a claim comment is for. The test is whether the confidence in the words is paid for by the evidence in the package. Politeness, length, and emoji are not graded here; substance is. | required |
| control-run | The repro report's artifacts, looked at for a second run that does not trigger the bug | The report shows a control: the same command or input shifted off the failing case, completing normally, or the behavior's absence on a version the issue says is unaffected. This never changes a verdict. It separates a report that isolated the failure from one that merely captured it. | preferred |

## Verdict rule

`accept` (ready to post) if every **required** check passes. Any required
`fail` holds the package.

`unclear` on a required check counts as `fail`, and the summary must say so in
those words -- held for *insufficient evidence*, not on established bad
evidence. The two call for different repairs. A required check that keeps
returning `unclear` is saying its evidence column points at something packages
do not reliably contain, which is a defect in the check rather than in its
threshold.

`preferred` checks never change the verdict. Report their grades, and name them
in the summary as what separates a strong package from a merely sufficient one.

On a claim-only draft, the checks whose evidence is the repro report
(`behavior-matches`, `input-matches`, `claims-backed`, `outcome-honest`,
`env-recorded`, `steps-followable`, `control-run`) are reported `unclear` with
the evidence line `not yet applicable: claim-only draft` and left out of the
verdict, per SKILL.md. The verdict then rests on `claim-grounded` and
`conventions-respected` alone, and answers only whether the claim is ready.
